Part 1 · Fundamentals

How a URDF is written

Before the real robot, the basics: what a description is made of and the rules that hold it together. If you already know URDF, skip to Part 2.

01 / Links

Links — the rigid parts

A URDF describes a robot as a set of links — rigid bodies like the chassis, a wheel, or a sensor housing — plus the connections between them. Each link can carry three blocks:

  • visual — the shape you see (box, cylinder, sphere or a mesh) and its colour.
  • collision — a usually simpler shape the physics engine uses for contact.
  • inertial — mass and the inertia matrix, so physics knows how it moves.
a single link 
<link name="base_link">
  <visual>
    <geometry><box size="0.3 0.2 0.1"/></geometry>
    <material name="grey"><color rgba="0.5 0.5 0.5 1"/></material>
  </visual>
  <collision>
    <geometry><box size="0.3 0.2 0.1"/></geometry>
  </collision>
  <inertial>
    <mass value="1.0"/>
    <inertia ixx="0.01" ixy="0" ixz="0" iyy="0.01" iyz="0" izz="0.01"/>
  </inertial>
</link>

On its own a link just floats in space — it has no idea where it belongs until a joint attaches it to something.

02 / Joints

Joints — parent & child

A joint connects exactly two links: a parent and a child. It says where the child sits relative to the parent and how it is allowed to move. Chain these parent→child relationships and the robot becomes a single tree: one root link at the top, every other link hanging below it, and no loops.

The joint's origin places the child relative to the parent; axis sets the direction it turns or slides. The type decides the motion:

  • fixed — no movement; rigidly attached (sensors, mounts).
  • continuous — rotates without limit (wheels).
  • revolute — rotates within limits (an arm hinge).
  • prismatic — slides in a straight line.
a joint 
<joint name="wheel_joint" type="continuous">
  <parent link="base_link"/>
  <child  link="wheel_link"/>
  <origin xyz="0.1 0.15 0" rpy="0 0 0"/>
  <axis   xyz="0 1 0"/>
</joint>
03 / Assemble

A complete URDF

Put a few links and joints inside one <robot> element and you have a valid URDF. Every link must have a path back to the root through joints — a link with no joint is “floating” and won't appear. Here's a whole (tiny) two-wheel robot:

mini_bot.urdf 
<?xml version="1.0"?>
<robot name="mini_bot">

  <link name="base_link">   ...   </link>
  <link name="left_wheel">  ...   </link>
  <link name="right_wheel"> ...   </link>

  <joint name="left_wheel_joint" type="continuous">
    <parent link="base_link"/>
    <child  link="left_wheel"/>
    <origin xyz="0 0.15 0"/>
    <axis   xyz="0 1 0"/>
  </joint>

  <joint name="right_wheel_joint" type="continuous">
    <parent link="base_link"/>
    <child  link="right_wheel"/>
    <origin xyz="0 -0.15 0"/>
    <axis   xyz="0 1 0"/>
  </joint>

</robot>

Run check_urdf on it and you'd see base_link as the root with two wheels attached — a complete, loadable robot.

04 / Xacro

Xacro — URDF without copy-paste

Plain URDF gets repetitive fast — two wheels already duplicate a whole block, four is worse. Xacro (XML Macros) is URDF with three extras: properties (named constants), math inside ${...}, and macros (reusable blocks with parameters). It expands back into ordinary URDF before use.

mini_bot.xacro 
<robot xmlns:xacro="http://www.ros.org/wiki/xacro" name="mini_bot">

  <xacro:property name="wheel_r" value="0.05"/>

  <xacro:macro name="wheel" params="name y">
    <link name="${name}"> ... </link>
    <joint name="${name}_joint" type="continuous">
      <parent link="base_link"/>
      <child  link="${name}"/>
      <origin xyz="0 ${y} 0"/>
      <axis   xyz="0 1 0"/>
    </joint>
  </xacro:macro>

  <xacro:wheel name="left_wheel"  y="0.15"/>
  <xacro:wheel name="right_wheel" y="-0.15"/>

</robot>

Define the wheel once, call it per side. That's exactly how the Wes Car below builds four mecanum wheels from a single macro — so with the fundamentals in place, let's read the real file.

Part 2 · The Wes Car

Building the mecanum AGV

Everything below is the actual wes_car.urdf.xacro from the repo — a Yahboom ROSMASTER M1 mecanum base. Same ideas as above, applied for real.

05 / Frame tree

The frame tree

A URDF describes a robot as a tree of links (rigid bodies) joined by joints. This AGV is one Xacro file with a single root, base_footprint (the Nav2 convention — the body's shadow on the floor); everything else hangs off base_link.

frame tree 
base_footprint              # root — ground projection
└─ base_link                # chassis (ROSMASTER M1 mesh)
   ├─ wheel_lf_link         # ┐ four mecanum wheels,
   ├─ wheel_rf_link         # │ continuous joints
   ├─ wheel_lb_link         # │
   ├─ wheel_rb_link         # ┘
   ├─ lidar_link            # SLAMTEC RPLIDAR C1 → /scan
   └─ camera_link           # Nuwa-HP60C depth camera
      └─ camera_optical_link # ROS optical frame

The whole file is Xacro (XML macros), so it opens with the namespaced <robot> tag and leans on properties and a macro to avoid repeating the four wheels.

06 / Parameters

Dimensions as properties

Every real dimension lives in one place as an <xacro:property>, taken from the official SolidWorks measurements. Later blocks reference them with ${...}, so tuning the robot means editing one number instead of hunting through the file.

wes_car.urdf.xacro 
<robot xmlns:xacro="http://www.ros.org/wiki/xacro" name="wes_car">

  <xacro:property name="wheel_radius"   value="0.034"/>   <!-- contact radius -->
  <xacro:property name="wheel_width"    value="0.037"/>
  <xacro:property name="wheel_mass"     value="0.102"/>
  <xacro:property name="front_x"        value="0.08"/>    <!-- front axle vs. centre -->
  <xacro:property name="rear_x"         value="-0.11"/>   <!-- rear axle vs. centre -->
  <xacro:property name="half_track"     value="0.08475"/> <!-- half wheel track (y) -->
  <xacro:property name="base_mass"      value="1.116"/>
  <xacro:property name="base_z"         value="0.065"/>   <!-- base_link height off ground -->

  <xacro:property name="lidar_offset_x"  value="0.010"/>
  <xacro:property name="lidar_offset_z"  value="0.151"/>
  <xacro:property name="camera_offset_x" value="0.096"/>
  <xacro:property name="camera_offset_z" value="0.084"/>

  <material name="grey"><color rgba="0.5 0.5 0.5 1"/></material>
  <material name="black"><color rgba="0.1 0.1 0.1 1"/></material>
  <material name="blue"><color rgba="0.2 0.4 0.8 1"/></material>

Note the asymmetric front_x / rear_x — the chassis centre isn't the geometric centre, so the axles sit at different distances fore and aft.

07 / Base

base_footprint & base_link

The root is an empty base_footprint link; a fixed joint lifts the chassis to base_z above it. The chassis uses a lightweight .stl mesh for looks, a simple box for collision (far cheaper than the mesh), and the official mass and inertia.

base 
<link name="base_footprint"/>

<joint name="base_joint" type="fixed">
  <parent link="base_footprint"/>
  <child  link="base_link"/>
  <origin xyz="0 0 ${base_z}" rpy="0 0 0"/>
</joint>

<link name="base_link">
  <visual>
    <origin xyz="-0.139423 -0.075781 -0.0439" rpy="0 0 0"/>
    <geometry>
      <mesh filename="package://simulation/meshes/rosmaster_m1_lite.stl"
            scale="0.001 0.001 0.001"/>
    </geometry>
    <material name="grey"/>
  </visual>
  <collision>                       <!-- simplified box, not the 63M-vertex mesh -->
    <origin xyz="0 0 0.03" rpy="0 0 0"/>
    <geometry><box size="0.28 0.2 0.12"/></geometry>
  </collision>
  <inertial>
    <mass value="${base_mass}"/>
    <inertia ixx="0.00183" ixy="0" ixz="0" iyy="0.00349" iyz="0" izz="0.00473"/>
  </inertial>
</link>

Keeping visual and collision geometry separate is a common trick: a pretty mesh you can see, a crude box the physics engine can solve fast.

08 / Wheels

The mecanum-wheel macro

All four wheels come from one <xacro:macro>. Two details make mecanum motion actually work in gz-sim: the collision is a sphere (a cylinder makes the solver fail), and each wheel gets an anisotropic friction direction fdir1 at ±45°, matching the physical rollers.

mecanum_wheel macro 
<xacro:macro name="mecanum_wheel" params="prefix x reflect_y fdir">
  <link name="wheel_${prefix}_link">
    <visual>
      <origin xyz="0 0 0" rpy="${pi/2} 0 0"/>
      <geometry><cylinder radius="${wheel_radius}" length="${wheel_width}"/></geometry>
      <material name="black"/>
    </visual>
    <collision>                       <!-- sphere: key to gz-sim MecanumDrive -->
      <geometry><sphere radius="${wheel_radius}"/></geometry>
    </collision>
    <inertial>
      <mass value="${wheel_mass}"/>
      <inertia ixx="4.6e-05" ixy="0" ixz="0" iyy="7.5e-05" iyz="0" izz="4.6e-05"/>
    </inertial>
  </link>

  <joint name="wheel_${prefix}_joint" type="continuous">
    <parent link="base_link"/>
    <child  link="wheel_${prefix}_link"/>
    <origin xyz="${x} ${reflect_y * half_track} ${wheel_radius - base_z}" rpy="0 0 0"/>
    <axis xyz="0 1 0"/>
  </joint>

  <gazebo reference="wheel_${prefix}_link">   <!-- roller friction -->
    <mu1>1.0</mu1> <mu2>0.0</mu2> <fdir1>${fdir}</fdir1>
  </gazebo>
</xacro:macro>

<!-- X-pattern rollers: LF/RB one diagonal, RF/LB the other -->
<xacro:mecanum_wheel prefix="lf" x="${front_x}" reflect_y="1"  fdir="0.7071 -0.7071 0"/>
<xacro:mecanum_wheel prefix="rf" x="${front_x}" reflect_y="-1" fdir="0.7071  0.7071 0"/>
<xacro:mecanum_wheel prefix="lb" x="${rear_x}"  reflect_y="1"  fdir="0.7071  0.7071 0"/>
<xacro:mecanum_wheel prefix="rb" x="${rear_x}"  reflect_y="-1" fdir="0.7071 -0.7071 0"/>

The fdir1 vector must be expressed in the body frame; because URDF→SDF conversion strips that attribute, the real project re-injects it in sim.launch.py after the SDF is built. The spin axis is 0 1 0 (the y-axis), and reflect_y mirrors left/right.

09 / Sensors

Lidar & depth camera

Two sensors hang off base_link with fixed joints, placed by the offset properties. The camera adds a second camera_optical_link rotated into the ROS optical convention (z-forward, x-right, y-down) — image and point-cloud topics use that frame.

sensors 
<!-- SLAMTEC RPLIDAR C1 -->
<link name="lidar_link">
  <visual><geometry><cylinder radius="0.0278" length="0.0413"/></geometry><material name="black"/></visual>
  <collision><geometry><cylinder radius="0.0278" length="0.0413"/></geometry></collision>
  <inertial><mass value="0.11"/>
    <inertia ixx="0.0001" ixy="0" ixz="0" iyy="0.0001" iyz="0" izz="0.0001"/></inertial>
</link>
<joint name="lidar_joint" type="fixed">
  <parent link="base_link"/>
  <child  link="lidar_link"/>
  <origin xyz="${lidar_offset_x} 0 ${lidar_offset_z}" rpy="0 0 0"/>
</joint>

<!-- Nuwa-HP60C depth camera -->
<link name="camera_link">
  <visual><geometry><box size="0.025 0.09 0.025"/></geometry><material name="blue"/></visual>
  <collision><geometry><box size="0.025 0.09 0.025"/></geometry></collision>
  <inertial><mass value="0.1"/>
    <inertia ixx="0.0001" ixy="0" ixz="0" iyy="0.0001" iyz="0" izz="0.0001"/></inertial>
</link>
<joint name="camera_joint" type="fixed">
  <parent link="base_link"/>
  <child  link="camera_link"/>
  <origin xyz="${camera_offset_x} 0 ${camera_offset_z}" rpy="0 0 0"/>
</joint>

<!-- optical frame: ROS convention z-forward, x-right, y-down -->
<link name="camera_optical_link"/>
<joint name="camera_optical_joint" type="fixed">
  <parent link="camera_link"/>
  <child  link="camera_optical_link"/>
  <origin xyz="0 0 0" rpy="${-pi/2} 0 ${-pi/2}"/>
</joint>
10 / Simulation

Embedded gz-sim systems

The same file carries the Gazebo Sim plugins, so the model drives itself once spawned. MecanumDrive subscribes to cmd_vel (a Twist with linear.y for strafing) and spins the four wheels; separate OdometryPublisher and JointStatePublisher systems put out odometry and wheel TF. Wiring the world, bridge and sensors is covered in the Gazebo guide.

MecanumDrive system 
<gazebo>
  <plugin filename="ignition-gazebo-mecanum-drive-system"
          name="ignition::gazebo::systems::MecanumDrive">
    <front_left_joint>wheel_lf_joint</front_left_joint>
    <front_right_joint>wheel_rf_joint</front_right_joint>
    <back_left_joint>wheel_lb_joint</back_left_joint>
    <back_right_joint>wheel_rb_joint</back_right_joint>
    <wheel_separation>${2 * half_track}</wheel_separation>
    <wheelbase>${front_x - rear_x}</wheelbase>
    <wheel_radius>${wheel_radius}</wheel_radius>
    <topic>cmd_vel</topic>
  </plugin>
</gazebo>
11 / Build

Expand, check & launch

Xacro isn't valid URDF until expanded. Expand it, validate the tree, then launch the real project:

terminal 
# expand the xacro and validate the tree
xacro wes_car.urdf.xacro > /tmp/wes_car.urdf
check_urdf /tmp/wes_car.urdf

# publish robot_description + robot_state_publisher, then spawn into gz-sim
ros2 launch simulation sim.launch.py

check_urdf prints the link hierarchy so you can confirm base_footprint is the root and all four wheels plus both sensors are attached. From here, take it into the Gazebo world to drive it.
