LAB.01 / Gazebo Guide 模擬世界教學

Driving the robot
in a simulated world

Once the URDF describes the robot, Gazebo turns it into something you can actually drive — a world with gravity, friction and sensors. This guide builds a Gazebo world for the mecanum AGV: spawning the model, wiring the mecanum-drive plugin, tuning friction and adding simulated lidar and camera.

← Back to Build URDF Guide
01 / Concept

URDF vs. the world

Two files play different roles. The URDF describes the robot itself — its links and joints. The world (an SDF file) describes everything around it: the ground plane, lighting, gravity and physics settings. Gazebo loads the world first, then spawns your URDF model into it.

  • .urdf / .xacro — the robot, from the URDF guide.
  • .world / .sdf — the environment the robot lives in.
  • A launch file ties them together and starts Gazebo.
02 / World

A minimal world file

A world needs at least a physics engine, a light and a ground plane. Start from Gazebo's built-in models so you don't have to model the floor and sun yourself.

wes_car.world 
<?xml version="1.0"?>
<sdf version="1.9">
  <world name="wes_car_world">

    <physics name="1ms" type="ignored">
      <max_step_size>0.001</max_step_size>
      <real_time_factor>1.0</real_time_factor>
    </physics>

    <plugin filename="gz-sim-physics-system"
            name="gz::sim::systems::Physics"/>
    <plugin filename="gz-sim-sensors-system"
            name="gz::sim::systems::Sensors">
      <render_engine>ogre2</render_engine>
    </plugin>

    <include>
      <uri>https://fuel.gazebosim.org/1.0/OpenRobotics/models/Sun</uri>
    </include>
    <include>
      <uri>https://fuel.gazebosim.org/1.0/OpenRobotics/models/Ground Plane</uri>
    </include>

  </world>
</sdf>

Launching this with gz sim wes_car.world should give you an empty, lit room with a floor — ready for the robot.

03 / Drive

The mecanum-drive plugin

Gazebo needs a plugin to turn /cmd_vel into wheel motion. For a mecanum base, the mecanum-drive system spins all four wheels independently so the robot can move sideways and rotate in place. Add this inside the robot's URDF (or as a <gazebo> block) so it travels with the model.

gazebo plugin 
<gazebo>
  <plugin filename="gz-sim-mecanum-drive-system"
          name="gz::sim::systems::MecanumDrive">
    <front_left_joint>wheel_fl_joint</front_left_joint>
    <front_right_joint>wheel_fr_joint</front_right_joint>
    <back_left_joint>wheel_rl_joint</back_left_joint>
    <back_right_joint>wheel_rr_joint</back_right_joint>
    <wheel_separation>0.28</wheel_separation>
    <wheelbase>0.24</wheelbase>
    <wheel_radius>0.05</wheel_radius>
    <topic>cmd_vel</topic>
  </plugin>
</gazebo>

The four joint names must match the ones from the URDF exactly. wheel_separation and wheelbase come straight from the joint origins you set earlier.

04 / Physics

Friction & inertials

A model with no friction slides like it's on ice; wrong inertials make it flip. Each wheel needs a <gazebo reference> block that sets its friction coefficients, and every link needs believable mass and inertia (set back in the URDF).

per-wheel friction 
<gazebo reference="wheel_fl">
  <mu1>1.0</mu1>
  <mu2>1.0</mu2>
  <kp>1000000.0</kp>
  <kd>100.0</kd>
</gazebo>
  • mu1 / mu2 — friction along and across the wheel; mecanum rollers usually want these tuned lower sideways.
  • kp / kd — contact stiffness and damping; too soft and the wheels sink into the floor.
05 / Sensors

Simulated lidar & camera

The same lidar and camera the real robot uses can be simulated. Attach a sensor to a link and add the matching Gazebo sensor plugin — Gazebo then publishes /scan and image topics just like the hardware drivers do.

lidar sensor 
<gazebo reference="lidar_link">
  <sensor name="lidar" type="gpu_lidar">
    <topic>scan</topic>
    <update_rate>10</update_rate>
    <lidar>
      <scan>
        <horizontal>
          <samples>360</samples>
          <min_angle>-3.14159</min_angle>
          <max_angle>3.14159</max_angle>
        </horizontal>
      </scan>
      <range>
        <min>0.12</min>
        <max>12.0</max>
      </range>
    </lidar>
  </sensor>
</gazebo>

Because the simulated sensor publishes the same topic names, the rest of the ROS2 stack can't tell it apart from the real one — which is exactly what makes sim useful.

06 / Launch

Spawn & bridge to ROS2

Finally, tie it together: start the world, spawn the URDF, and bridge Gazebo topics to ROS2 with ros_gz_bridge so /cmd_vel and /scan flow both ways.

terminal 
# start Gazebo with the world
gz sim wes_car.world

# spawn the robot from its URDF
ros2 run ros_gz_sim create -topic robot_description -name wes_car

# bridge cmd_vel and scan between ROS2 and Gazebo
ros2 run ros_gz_bridge parameter_bridge \
  /cmd_vel@geometry_msgs/msg/Twist@gz.msgs.Twist \
  /scan@sensor_msgs/msg/LaserScan@gz.msgs.LaserScan

# or launch the whole sim in one shot
ros2 launch wes_car_bringup sim.launch.py

Drive it with a teleop node or a joystick publishing to /cmd_vel. Once the car moves in Gazebo and the lidar paints obstacles, the simulation matches the real robot closely enough to test navigation before any hardware is powered on.
